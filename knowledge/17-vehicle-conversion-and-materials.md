# 17. Vehicle conversion FS19 → FS25: models, materials, textures

[← Overview](../README.md)

Learned while converting an FS19 tipper trailer to FS25 (November 2026). Status markers as everywhere: ✅ confirmed in game · 📖 read from game files (shaders, XSD, base-game XML) · ❓ assumption.

## Workflow without Blender

- Open the FS19 i3d once in **GIANTS Editor 10** and save it → geometry is in the FS25 format (`.i3d.shapes` version 10). Everything else can be scripted. ✅
  - GIANTS Editor merges materials whose FS19 textures are missing (they become identical) and reassigns `materialIds` – e.g. a drawbar or decal suddenly uses the body material. Take the scene and `shapeId`s from the saved file but `<Files>`, `<Materials>` and every shape's `materialIds` from the FS19 original (nodes are in the same order). ✅
  - FS19 `.i3d.shapes` are version 5 and parse with the same reader; writing them as v10 yourself works for geometry, but the editor also adds convex collision data (`cm` attachment) to compound collision shapes – keep the editor step. 📖
- **Reading `.i3d.shapes`:** the pure-Python reader of [blender-i3d-importer](https://github.com/nadine-brinkmann/blender-i3d-importer) (GPLv3) works without Blender (`i3d_shapes_reader`, `i3d_shapes_models`, `_cipher_keys`).
- **Writing `.i3d.shapes` v10** (own writer, verified by a byte-identical read→write roundtrip ✅). Shape entity layout:
  name (int32 length + bytes, pad to 4) · id · bounding volume (4 floats, not for type 5) · cornerCount, numSubsets, vertexCount, options · `vtxCompression` float (v ≥ 9) · subsets (4 × uint32 + one float UV density per present UV set) · **material slot names** (uint16 length + bytes, pad to 2, then to 4) · indices (uint16 if vertexCount ≤ 0x10000, else uint32; pad to 4) · positions · normals · tangents (4 floats) · UV sets · vertex colours · skinning (weights only if not single-weight, then index bytes) · generic data · remaining attachment bytes unchanged.
  File: header `[version, 0, seed, 0]`, then every chunk (count; per entity type, size, data) encrypted separately with a running block index.
- Check results without starting the game: rasterise the mesh to a 2D sketch (orthographic, colour per subset, optional texture overlay).
- Limits: reordering, hiding, recolouring and adding simple quads works; real modelling or new UVs need Blender.

## Materials

- **Washed-out colours:** every `vehicleShader` material needs `<Texture>` pointing to `$data/shared/white_diffuse.png`; remove the FS19 `diffuseColor`. ✅
- FS19 `_specular` and FS25 `_vmask` have the **same channel layout**: R scratches, G baked AO, B dirt. Renaming is enough. 📖✅
- **FS19 colorMask rule** (FS19 vehicleShader): `uv.y < 0` → paint zone `colorMat[floor(uv.x)]`, otherwise `DetailArray[floor(u) + floor(v)*8]` (fixed materials, e.g. 2 chrome, 5 rubber, 8 silver metallic, 14 wood, 21/22 red/orange reflector). Using only `floor(u)` gives wrong zones. 📖✅
- **Colour configurations need slot names in the `.i3d.shapes` file** (one per subset). Names only in the i3d XML give "Failed to find material by material slot name". Split each colorMask mesh into one subset per zone and write the slot names. ✅
- Official brand colours: `data/shared/brandMaterialTemplates.xml`; own templates in the modDesc `<materialTemplates>` with `parentTemplate` (`calibratedPaint`, `wood2`, `silverScratched` …). Detail templates: `data/shared/detailLibrary/materialTemplates.xml`. 📖
- Decals must not sample the body vmask with UV1 (smeared). Base-game way: `customShaderVariation="vmaskUV2"` with the body vmask as glossmap – the decal's **second UV set** points to the body texture under it, so decals get the same dirt as the wall. FS19 decals already have that UV2. Add `alphaBlendingClipThreshold 1` and detail maps (`metalPainted_diffuse/_specular`, `flat_normal`). ❓
- Base-game decal shapes use `castsShadows="false"`; with shadows the thin decal layer looks noisy. ❓
- FS19 reflectors (variation `reflector`) have UV1 spread across the whole texture (old DetailArray tile), so the body vmask gives random dirt there. A plain square mask gets stretched enormously by those UVs (big blotches; tiny UV2 areas turn fully brown). Measure world size vs UV size per triangle first: FS19 reflector UVs were uniformly scaled but partly rotated 90°, so per-region pre-stretching produced wood-grain streaks. A square own vmask (R=0, G=255, B=direction-less grain at real-world scale, uncompressed) works. Decals whose UV2 matches the body stay on the body vmask. ❓
- Bare metal (silver parts) needs much less dirt than paint – the same mask value reads as thick stuck mud on metal. Lower it (~30 %) only where the texture area is not shared with painted parts. ❓
- **A vehicleShader material without detail maps shows the engine's default detail texture** – a test pattern with numbers and crosshairs, plus glitter. Give every material its own `detailDiffuse/Normal/Specular`. 📖
- **Reflectors like the base game:** copy the `reflectorYellow/Orange/Red` templates from `detailLibrary/materialTemplates.xml` (colorScale, `clearCoatIntensity 0.25`, `clearCoatSmoothness 1.0`, detail maps `nonMetallic/reflector/reflector_diffuse/_specular` + `flat_normal`) – this gives the prismatic honeycomb look. Base-game trailers do not use the `reflector` shader variation. ❓
- Collision masks: FS19 `8397058`/`8194` → `collisionFilterGroup 0x10004`, `collisionFilterMask 0xfe3ffb83`; `1073741824` → `0x40000000 / 0x20000000`. ✅
- HD warning stickers: FS25 atlas `$data/shared/assets/assetLibraryStickers_diffuse` (4096², 16 × 8 cells of 256 px). ✅

## Textures: what FS25 shows that FS19 hid

- **Clear coat reveals normal-map compression blocks** of old textures as speckles in highlights. Fix: replace isolated deviating pixels in flat surroundings with the local median (e.g. 13 × 13 window, only where ≥ 70 % of the window is flat). ✅
- **Dirt formula** (FS25 vehicleShader, vmask B): `dirt = linearstep(1-d, 1.5-d, B)`, `dust = B * d` (`d` = dirt amount 0–1). Small B values already give visible dirt, **including the rough dirt normal and specular**. 📖✅ Consequences:
  - A thin dirt film everywhere makes the whole paint look grainy. Use spots with **B = 0** in between, like base-game trailers.
  - DXT1 quantises B per 4 × 4 block → mosaic. Store a hand-made dirt vmask uncompressed (BGRA8 with mipmaps). ✅
  - Distribute dirt by **world height** (rasterise vertex height into UV space): dirty at the bottom and chassis, almost clean at the top; base-game covers have B ≈ 0. ✅
  - Convert any copied grain/noise to **texels per metre** of the target model; mirrored tiling shows as a kaleidoscope once you threshold it – generate non-tiled noise instead.
- **Base-game dirt is hand-painted and instanced per panel:** e.g. on the Rudolph DK 280 RP all wall panels of one kind share one UV rectangle in the vmask (stored upside down), with dirt collecting at each panel's lower edge. Procedural noise does not reach that look; transferring such a panel rectangle onto your own panels (between the struts, cropped to real-world scale) gets much closer. ❓
- **Repeated dirt on instanced UVs:** old models often share one UV area between both sides and mirrored halves, so a hand-painted dirt pattern repeats (and mirrors). Without re-unwrapping: add a **second UV set used only by the vmask** (`customShaderVariation="vmaskUV2"` on every material using that texture): UV2 = frac(UV1) scaled into part of the vmask, and each instance gets its own area in the freed space. Give every visible wall face its own full-resolution area – squeezed areas look washed out. Against repetition, combine two source crops per panel with `max()` (keeps edges crisp; averaging blurs). The normal map stays on UV1. ❓
- **Detail textures are world-space:** `detailDiffuse/Normal/Specular` are sampled triplanar from `localPosition` (1 tile = 1 m), independent of the UVs. Useful for even surface structure (e.g. tarp weave) on badly unwrapped old models. 📖 ❓ (result in game not confirmed yet)
- **No paint wear on the body:** FS19 masks often have an empty R channel (scratches/wear), so FS25 shows almost no wear there. Base-game masks (Rudolph) use thin bright lines along UV island borders and bevels plus a little surface noise (mean ≈ 2/255, p99 ≈ 50). Generate it: only on painted materials, edges = island border (2 px) + bevels detected from the normal map (tilt > ~0.22), broken up by fractal noise, stronger low on the vehicle; on large wall panels add light wear increasing downwards and a few fine horizontal scratches. Combine with any existing R by max(). **Keep it at the reference statistics** – surface noise and scratches on large panels turned into big pale blotches at high wear in game; edges of struts/frame only, mean ≈ 2/255, p99 ≈ 50, was still too much when concentrated on the struts; mean ≈ 1, p99 ≈ 22 is the current try. Wear concentrated on narrow parts reads much stronger than the same statistics spread over a whole vehicle. ❓
- A colour configuration applies the whole material template, including detail maps. Keep own detail maps with `<material materialSlotName="…" materialTemplateUseColorOnly="true"/>`. 📖

- **Keep the mod size close to comparable base-game vehicles.** FS25 itself uses **BC7** (DDS DX10, DXGI format 98, e.g. `dashboardSymbols_diffuse`). BC7 keeps a hand-made dirt channel nearly lossless (~1.6/255 mean error) at ¼ of the uncompressed size – use it instead of uncompressed masks. **Not for textures that need transparency:** a BC7 decal texture rendered with its alpha ignored (black rectangles, flickering overlapping decals) – keep decals as DXT5/BC3 with a classic DDS header. ✅ Self-written BC7 files log `(BC7) has undefined channel count, assuming 3 channels`. Base-game DDS files carry a block in `dwReserved1` (bytes 32–75): magic `D9 E8 8A 28`, `0`, then `8` (DXT1) or `12` (every base-game BC7, including decals with alpha), then a 16-byte checksum (not the file MD5). Writing magic + 12 + MD5 of the image data is the current attempt to silence the warning (and probably why BC7 decals lost their alpha before). ❓
- **Blocky patches on long, thin parts (drawbars, ladder steps, frame rails):** old models put long parts on UV strips only 2–16 px wide. The DXT1 normal map breaks the bevel lines at the strip edges into 4 × 4 block dashes and the baked AO is noisy along the strip – FS25 clear coat makes both visible as stepped dark rectangles. Fix without re-unwrapping: find triangles with a small UV height and a long edge (> 4× height); for horizontal strips replace each texel row by its median **along** the strip (vertical strips: per column), including a 1 px border, skipping texels shared with wide triangles. This keeps the cross profile (bevel) and removes blocks and noise. Do it for the normal map (UV1) and the AO channel, renormalise normals and save as **BC7** – DXT1 would bring the blocks back. ❓
- **Deblocking old DXT1 textures:** re-saving as BC7 alone does not help – the 4 × 4 blocks are already in the data. Clean first: an edge-preserving **bilateral filter** (radius 4, spatial σ 2, value σ 10) removes the small block steps and keeps bevels; smooth low-frequency areas such as tarp wrinkles additionally (Gaussian σ ≈ 4 inside the island, then renormalise). Baked AO often has a noisy 1–3 px seam at UV island borders that shows as dark notches on edges: rasterise UV coverage, erode 2 px as "trusted", refill the ±2 px seam from the nearest trusted texel. Then save as BC7; keep textures with alpha as DXT5. ❓
- Small FS19 stickers with text (type plates) cannot be upscaled meaningfully – redraw them (render text at 4× and downscale), place them in an **unused area** of the same decal texture and move the quad's four UVs there: more pixels without a bigger texture. ❓
- Before upscaling a texture, rasterise which UV areas the shapes actually use – old decal atlases often contain unused parts (e.g. warning symbols that already come from the game's sticker atlas).

## Configurations

- Yes/No options: `isYesNoOption="true"` on the container (cover, design2, trailer …); the first entry is "No". ✅
- **Hiding parts of a merged mesh:** each vertex has one bone. Add a `TransformGroup` at identity under the same parent, append it to `skinBindNodeIds`, move the part's vertices to that bone, then `objectChange` it. ✅
- **Removable cover:** put the `objectChange` on the cover's **parent** – the `toggleCover` animation resets the visibility of the cover node itself. ✅
- **Rim colour:** `<rimColorConfigurations useDefaultColors="true" price="…">` with `rimColorConfiguration materialTemplateName="…"` (`RIM_DEFAULT`, `RIM_CONFIGURATION_CHROME`, `RIM_CONFIGURATION_BLACK`, `SHARED_GREYLIGHT` …). ✅
- **Own hub colour selection:** in `<wheels>` `<hubMaterial useDesignColorIndex="4"/>` plus a `designColor4Configurations` block without material slot. `hubMaterial` accepts `materialTemplateName`, `useBaseColor`, `useRimColor`, `useDesignColorIndex` (1–16); `designColor` … `designColor16Configurations` exist. ✅
- **License plate:** replace an FS19 modelled plate by an empty `TransformGroup` at the plate centre (rotation `0 180 0` at the back) **in the same place in the scenegraph** (keeps all index paths valid) plus `<licensePlates><licensePlate node="…" position="BACK" preferedType="ELONGATED" placementArea="top right bottom left"/></licensePlates>` (base game: `0.1 0.27 0.1 0.27`). ❓
- **Plate lights** (`plateNumberLight01`): base-game orientation is `rotation="-90 0 -90"` on the left (−x) node and `-90 0 90` on the right (+x) – both shine inward. ❓
- **Drawbar springs:** base-game springs are a plain cylinder with end eyes – the coils are in the texture – stretched by a `movingPart` with `scaleZ="true"` towards a reference node. When swapping, measure the rest length (node → `referencePoint`) and only stretch the new mesh slightly, or the painted coils pull apart.Split old and new parts by **connected triangle groups**, not by a z cut (a z cut clips the turnbuckle eye and leaves bits of the old hooks). Turn the front hook so it lies **perpendicular** to the eye it hangs in (rotate normals/tangents too), move the hooks undeformed and stretch only the coil body, and shear so both hook tips sit on the node axis – base-game spring meshes are modelled slightly offset. Keep the source normal map for the coils; recolour through a material that uses it. ❓
- **Material per configuration option:** any `…Configuration` accepts `<material materialSlotName="…" materialTemplateName="…"/>` (also `sourceMaterialSlotName`/`targetMaterialSlotName`, `useDesignColorIndex`; schema type `VehicleConfigurationDataMaterial`). Detail-library templates such as `reflectorYellow/Orange/Red` work as template names. Combine with `objectChange` for options like "warning stripes: none / yellow bottom / yellow bottom + top corners / orange … / red …". 📖 ❓
- **Lamp guards around shared lights (ReferenceNode):** base-game lights such as `lizard/rearLight31` are ReferenceNodes; their size is in their own i3d (rearLight31: x ±0.215, depth y 0..0.084, height ±0.076; local y = backwards, z = down). Build the cage from boxes in that lamp space inside a new TransformGroup next to the ReferenceNode with the same translation/rotation. For checking, place the light i3d with the ReferenceNode world matrix into the preview, and check what already sits in the cage volume. ❓
- **Take decal shapes along when making a part switchable:** screw heads are often separate decal shapes (`screws_decals`, `meshAffectedscrews*_decal`) next to the merged mesh. If only the mesh part is moved, the screws float in the air when the part is off. Search every shape (including those with `decalLayer`) for triangles inside the part's box and move them too. ✅ (seen in game)
- **Switchable part cut out of a mesh can leave a hole:** when an original part (e.g. a reflector band sitting in a recess of a rail) is moved into its own shape so it can be hidden, it is often the only surface there. Add a filler with the same geometry in the surrounding material (with that colour slot, so colour options still apply) as a sibling node, switched exactly the other way round. ✅ (seen in game: hole without the filler)
- **Moving an add-on part from one vehicle to another (drawbar step):** build a reference frame per drawbar arm from plane cross-sections (intersect triangle edges with z = const; vertex samples miss long triangles): centre line, direction in x-z, top/bottom edge, width. Rotate the part about y from arm A to arm B, keep the height relative to the top edge, stretch the part below the top edge to the new arm height, stretch inside / shift outside across the arm. A z-slice of a slanted arm is wider than the true width (÷ cos), so check the clamps in a top view limited to arm height. Take the source materials with their base-game textures along (the UVs only fit their own vmask). ❓
- **Window in a front wall without rebuilding it:** if the space between the stakes is free, take every triangle of the body bone that touches the window rectangle and lies fully within the wall depth out of the merged mesh; keep one copy as "original" and one per window size clipped against the rectangle (4 half-planes, attributes interpolated). A reveal from the smallest to the largest wall z hides ribs at the edge. With two LOD levels, put a LOD group (0/50 m) under the LOD0 bone with own wall variants per level. Check what lies behind the hole first. ❓
- **Adding warning stripes where the original has none:** ray-cast the wall cross-section in x per height to find a flat rib, then find the z ranges between stakes/joints where the whole band height lies on the same x (±1.5 mm). Put the band 3 mm in front of the surface as the **last child of the wall node** (it follows an opening side wall, and existing index paths stay valid). Build it from ~0.2 m pieces with their own vertices and take the **UVs of the wall underneath** (barycentric) so normal map and vmask match without a new texture; tangent from the UV gradient. Material: copy of the wall material with the reflector detail maps, colour per option through the `reflectorYellow/Orange/Red` templates on the slot. In the base-game Brantner trailers the side wall is not always in the main mesh: on the DD 24073 it is the separate shape `doorLeft/doorRight`, on the Z 18051 the bone `doorLeft` of the merged mesh (the LOD1 bone `doorLeft_lod` is its child, so one shape under the LOD0 bone is enough). 📖 ❓
- **Independent decal options:** old mods often stack decal variants as parent/child nodes (same shape, one material per atlas, each atlas holding only its part). Hiding the parent hides the child, so move the child to its own node at the **end of the group** (keep its combined translation) – other index paths stay valid. A colour variant needs no new geometry: same shape, material copy pointing to a recoloured atlas copy (e.g. white badge with cut-out letter → red badge with white letter: fill holes of the opaque area, colour = α·red + (1−α)·white, alpha 255 inside). ❓
- **Cutting a window into a surface without Blender:** move the affected triangles into two new shapes (full / with hole) as children of the original node and switch them via `objectChange`. Hole: clip each triangle against four half-planes (left, right, top-middle, bottom-middle → convex pieces), interpolate all attributes barycentrically, keep winding along the face normal. Glass: base-game window material (`$data/shared/window_diffuse.png`, `window_vmask.png`, `default_normal.png`, alphaBlending, detail `clear_diffuse`/`flat_normal`/`grainSmall_specular`), double-sided. Parts of a skinned merged mesh can be moved out the same way: put the new unskinned shapes **under the bone node** with positions = bind pose minus the bone node's world position; copy an existing unskinned shape with the same UV sets as template for the shape entry. ❓
- **Switching part of a shape:** move the triangles into a new shape (new shapeId appended to the .shapes) and link it as the **last child** of the old shape node – no other index paths move; add an `i3dMapping` for `…|0`. 📖 ❓
- **Moving parts to another colour zone** (e.g. door latches from paint to silver): find connected parts (weld by position, union-find) inside the subset, select by size/height/bone, reassign triangles and rebuild every subset's vertex and index range (duplicate shared vertices, permute all vertex attributes). Always render a preview – holders of ladders or marker lights tend to slip into the selection. Measure size limits on the real part instead of guessing (hinge forks of 16 cm fell out of a "< 15 cm" filter, only the pins changed). To recolour only part of a piece (e.g. drawbar eye black from the shoulder on), print its cross-section profile along the axis, find the step and split triangles by their min/max coordinate at an existing edge loop – centroids fail on long side quads that span the whole shank. Long profiles may have vertices only at their ends, so a rule like "smallest |x| of all vertices > 0.75" also matches a full-width rail: always limit the extent too. ❓
- **Shared working lights** (`$data/shared/assets/lights/lizard/workingLightNN.xml`): the model stands on its foot (local +y), the glass faces local +z. Hanging under a beam and facing backwards on a trailer whose rear is −z: `rotation="160 0 0"` (180 = level, 160 = slightly down). Square ones with a foot: 08, 09, 11, 12, 14, 17, 22, 31, 32. 📖 ❓ Render the lamp against the beam in a side section before shipping: a tilted housing easily ends up inside the beam (paint visible through the glass). Near 180° about x, local z flips – moving the node backwards moves the housing forwards. For **vertical** mounting faces use a lamp whose back is the mounting face and whose glass faces local +y: `workingLight10` (14 × 14 × 6 cm, square) or `workingLight13` (19 × 12 × 3 cm, flat LED panel); on a face pointing −z use `rotation="-90 0 0"`. Their XMLs define no function; set it like the base game with `<sharedLight … lightTypes="1"/>` (1 = rear work light, 2 = front). A `<function name="WORK_LIGHT_BACK"/>` child made the lamp light up with the normal driving lights in game (seen in game); the `lightTypes` fix is not confirmed yet. ❓
- **Aiming a shared working light at a point** (e.g. into the load area as an option): take the mounting position from the body's collision boxes, put a TransformGroup under the parent of the front-wall collision (so it tips with the body), compute the direction d in the parent frame and, for a lamp whose glass faces local +y (workingLight10), use rx = −acos(d_y), ry = atan2(d_x/sin rx, d_z/sin rx), rz = 0 (rotation order Rz·Ry·Rx). Switch it with `lightTypes="1"` and a configuration. The `linkNode` itself must not be hidden – the log says "Shared light link node … is hidden!" (seen in game ✅); let the configuration toggle a parent group and keep the link node inside it visible.
- **Shared working lights give no light cone on their own.** 📖 `workingLight10.xml` (and similar lizard lamps) only defines a `staticLightCompound` (the glowing glass), no light source; with the link node fixed the glass lit up but the load area stayed dark (seen in game ✅). The cone comes from your own `<Light type="spot">` node registered in `<lights><realLights><high>` with the same `lightTypes`, as the base-game rear work lights do. A spot light shines along its local −z: to align it with a lamp whose glass faces local +y, put it under the link node with `rotation="90 0 0"`. ❓ (in-game test pending)
- **Dirt on decals and add-on badges:** decal materials using `default_vmask` never get dirty. Without new textures: set UV1 of every decal vertex to the body UV0 at the nearest body point (shapes whose material reads the body vmask with UV0; `trimesh.proximity.closest_point` + barycentric interpolation), then give the material the body vmask and `customShaderVariation="vmaskUV2"`. Map interior decals (far from the body) to a clean vmask texel. An emblem that looks two-tone is often split across two materials (part plain decal, part chrome) – check that all its triangles share one material. A well-made FS25 MAN mod uses chrome geometry for lettering and trim and one chrome decal (diffuse atlas + its normal map) for the lion emblem. ❓
- **Adding small parts without Blender** (bolts, nuts, rivets): build simple prisms (hex head 6 sides + washer, round head as a 10-sided frustum), append them to the merged mesh with flat per-face normals, winding matched to the normal, the **bone of the carrying part** (so they move with doors), the silver subset, then rebuild subset ranges. Point all UV1 to one flat normal-map texel and all UV2 to one clean vmask texel; the detail texture provides the surface. Take positions from the cross-section of the carrying profile. ~35 triangles per bolt. ❓
- **Extra fixed colour for one part** (e.g. a black drawbar eye on a red drawbar): add a subset with its own slot name, copy the painted material with a fixed colorScale, and append the new material id to the shape node's `materialIds` (order = subset order). ❓
- **Look things up in the schema instead of guessing:** `<game install>/shared/xml/schema/vehicle.xsd` documents every vehicle XML path; also `wheel.xsd`, `wheelHub.xsd`, `materialTemplates.xsd`. 📖

## Physics

- **Converted trailers creep slowly over the ground:** FS19 values are usually `solverIterationCount="10"` on all components, no `inertiaScale` on the light dolly/drawbar components and a `brakeForce` without load scaling. Base-game drawbar trailer (Rudolph DK 280 RP): `solverIterationCount` 15/25/25, `inertiaScale="6 6 6"` on the dolly, `"2 2 2"` on the drawbar, `<brakeForce force="0.7" maxForce="1.5" maxForceMass="18000"/>` (brake force grows with the load). 📖 (effect in game not confirmed yet)

## Reusing parts from FS22 mods (with the author's permission)

- FS22 `.i3d.shapes` are version 7; the same reader parses them and the v10 writer can re-emit them (add material slot names, `vtxCompression` 0, keep the 4-byte attachment tail). FS22 colorMask uses the same zone rule as FS19, so split by zone into subsets with FS25 materials. ❓
- Insert foreign subtrees **at the same child index** as the node they replace (wrap several in one group) so all other index paths stay valid; convert index paths used in the XML (`localHose`). Base-game Rudolph textures moved to `$data/vehicles/rudolphSohn/shared/` in FS25.
- When deleting `i3dMapping` lines with a regex, remember node paths contain `>` – `[^>]*` stops inside `node="2>3|10"`.

## Connection hoses

- **Parked hoses without plugs:** FS25 places the plug of a detached hose at `adapterNode` (base game: `<hose … node="hydraulicIn01" adapterNode="hydraulicIn01_connector">`, the TG is a child of the `*_detached` shape at the hose end). Hoses taken from older mods may have such nodes but no `adapterNode` in the XML. Check the adapter sits on the hose end (distance to the nearest vertex of the parked hose mesh). 📖 ❓

- **Moving a hose group to a model with different geometry:** copy the subtree unchanged into a wrapper TG. Put the wrapper at the target point with the target tilt. Set the inner node to old position − old pivot. Child positions and mapping suffixes stay the same. Insert at the **same child index** as the node it replaces, or every later path (i3dMappings, localHose node paths) shifts. ✅ (loads without errors; in-game look pending)
- **Parked hose meshes are rigid:** test them against the new chassis, for example a wide drawbar box. If one intersects, rotate that mesh about its plug point (the adapter TG): t' = p − R·a. ❓ visual result pending

- **FS22 Rudolph materials:** the FS25 base game ships the Rudolph shared textures under `$data/vehicles/rudolphSohn/shared/` (dk280Shared01/02, tdk301Shared01/02, tdk301SharedAlpha01/02, *Hoses_vmask). FS22 parts that use them can be mapped zone by zone: one subset per colorMask zone, each with a detail-library material and these normal/vmask maps. Check the folder in the game install first. ✅ (files present)

- **Shape names differ from node names:** the name inside `.i3d.shapes` often differs from the node name in the `.i3d` (node "Leitung", shape "tdk301RP_vis.001"). Key per-part rules on the shape ID or the node, not on the shape name. ✅

- **Base-game parts on a mod vehicle:**
  - Standalone nodes can be loaded by reference with `dynamicallyLoadedParts` (filename, node, linkNode, position, rotation). 📖
  - Parts merged into the main mesh, or hoses shaped to another frame, have to be cut out instead.
  - Skinned base-game shapes are stored in model space (rest pose). To make them static, clear the skinning flag, drop the weights and indices, and recompute the bounding volume.
  - **Also clear `SINGLE_BLEND_WEIGHTS`** and the high option bit `0x80000000`. A shape that keeps these bits without skinning data **crashes the game** without a log message when the vehicle loads, for example in the shop. ✅
  - **Don't warp hoses onto a different frame.** A piecewise-linear map also stretches the tube cross-section, and round hoses turn into flat ribbons. ✅ (seen in game)
  - Build your own tubes along anchor points instead: Catmull-Rom spline, parallel-transport frames, 8 sides. Thin out straight runs and map the UVs onto a straight hose island of the base-game vmask. Base-game hoses have their face normals pointing the same way as the vertex normals. ✅ (looks good in game)
  - Spline pitfalls: add points along long straight runs, near the corners and every 0.3 m, or Catmull-Rom bulges by more than 10 cm. Remove duplicate points. Check tube-to-tube distance (KD-tree) and tube centerline against the mesh (trimesh `ProximityQuery`) before testing in game.

- **movingPart roll:** The game orients the node using the direction to the `referencePoint` and "up" = the y-axis of the `referenceFrame` (Cylindered.lua, `localDirectionToWorld(part.referenceFrame, 0, 1, 0)`). If the node is rolled about its axis in the i3d relative to that frame (e.g. `rotation="0 0 90"`), the first update rolls it back, and skinned parts such as cylinder trunnions visibly turn by 90°. Fix: give the node the frame's roll in the i3d and counter-rotate its children. 📖 ❓ (fix untested in game)
- **Routing tubes through a frame:** sample a free-space grid (distance from each grid point to all triangles) to find the gaps that cross members leave. Pick a height per section (high in front, under the cross members at the rear), keep a fixed order in the bundle, and put clips where they touch a cross member or a rail.

- **Stair-step artifacts on old models (raster):** the cause is long parts on narrow UV strips, plus blocky DXT1/BC1 normal and AO data. What helps:
  - median along each strip (keep the cross profile);
  - refill the island rims of the vmask and pad 3 px outward, then smooth AO and dirt only over used texels;
  - store as BC7.
  - A vmask shared by several models needs the triangles of all of them.
  ❓ in-game result pending
- **Alpha-tested gratings:** build the mips so that the share of texels at or above the alpha threshold stays the same in every level. Plain box mips soften alpha, so the bars break up in small mips. ❓

## Converting sister models

- When a second model of the same family uses the same FS19 texture atlas (e.g. a longer tipper), port the finished material definitions of the first one by material name (prefix swapped) instead of redoing them; only the main normal/vmask files and UV2-only variations differ. Derive the vehicle XML from the finished one: resolve `i3dMapping`s first from the FS19 XML of the new model (paths stay valid after the editor save), then by node name, and drop features whose nodes do not exist yet. Run a consistency check (mappings resolve, material/file/shape ids exist, XML slot names exist in the shapes, texture files exist) before handing it out. ❓

## Porting materials between i3d files ✅
- A material's `customShaderId="N"` points at a `<File>` entry. When copying materials from another i3d, make sure the target has `$data/shaders/vehicleShader.xml` under exactly that id. If that id is a texture instead, the log shows `Failed to open xml file '<some>.png'` plus `custommap "detailDiffuse" is not referenced in variation "base"` for every material, and all shapes using them are invisible.
- FS19 collision masks (e.g. 0x2002, 0x802102) trigger `Missing collision group/filter mask bit 16 (VEHICLE)`. Working trailer values: components and collision shapes group 0x10004, mask 0xfe3ffb83; exactFillRootNode group 0x40000000, mask 0x20000000.
- `Texture was flipped with quality loss: <file>.dds`: the engine flips the image vertically on the CPU while loading (message lives in `ImageUtil.cpp`). BC1–BC5 can be flipped losslessly by reordering blocks, BC7 cannot. Why only some textures get flipped is unknown ❓. Saving the affected vmask as BC1 (as GIANTS exports in other mods do) removes the warning ✅.
- The BC7 warning "has undefined channel count" disappears when the DDS carries the GIANTS block in dwReserved1 (magic 0x288ae8d9, 0, channel count, 16-byte checksum) – confirmed in game.

## Closing an opening in a mesh (option "without grain door") ✅
- Move the add-on parts into their own shape (last child of the same node, same local coordinates) and toggle it with objectChange.
- Build fill quads for each side of the hole. Get their UVs from an affine map (x, y, 1) → uv fitted by least squares to the vertices of the surrounding face in the same plane. For planar-mapped panels the error is about 0, so paint and dirt continue without a seam.
- Filling only the hole is not enough when the removed parts are painted into the textures (AO in the vmask, normal map): their shadows show up on the fill. Rebuild the whole panel from fields instead, and let the affected field use the UVs of its neighbour field, shifted by one post spacing, with the seams hidden under the posts. Check beforehand by sampling the texture through the UVs into an image.

- **Flickering usually means two nearly coincident faces:** before deleting a flickering part, look for faces of another part with the same normal less than 1 mm away (here a strip's inner face at x 1.2121 against the body at 1.2120). Moving it a few millimetres is usually enough; deleting it leaves a hole. ✅ (cause found; fix not yet tested in game)
- **Mounting a part flush without flicker:** a face may sit almost on top of another one if their normals point in **opposite** directions (a trim's inner face, normal −x, 0.2 mm in front of a wall's outer face, normal +x). From either side one of the two is back-face culled or hidden. Only faces with the same normal fight. Does not hold for double-sided materials. ❓
- **Merging duplicate textures without loss:** first rasterize which texels each vehicle actually uses (pull each triangle's UV back into one tile; diffuse/normal use UV1, the vmask uses UV2 with `vmaskUV2`) and compare candidate pairs only on used texels. For decal sheets build an atlas by copying the DXT blocks 1:1 with offsets that are multiples of 64 px, so mips 0–4 stay bit-identical and only the small mips are recomputed. FS19 decals often reuse **one mesh for several configuration variants** with different materials – give each variant its own shape copy before remapping UVs. Point empty (fully transparent) quads at a transparent texel. ✅
- **Compacting a decal atlas:** group the used triangles into islands (overlapping pixel boxes), copy only the pixels **under the triangles** (plus a few px margin) – unused stickers sitting next to a logo drop out automatically. Treat islands as duplicates only if the **maximum** pixel difference is small (type plates that differ only in a model number have a tiny mean difference). The same logo can also appear twice with different anti-aliasing or a few px offset; no simple metric (max/mean difference, blur, 3×3 tolerance) separates that reliably from plates with different text, so look at the packed result and merge true duplicates through an explicit alias list (find the offset by search). Send empty islands and degenerate triangles to one transparent cell. Pack with MaxRects (90° rotation allowed; for a counter-clockwise rotation x' = y, y' = width − x), lowering the scale until everything fits; merge a second sheet that uses the same material setup and repoint its Texture fileId. Verify without the game by sampling old texture/old UV against new texture/new UV at barycentric points of every triangle. If another model copies parts from this one in a build pipeline, freeze the source first or the UVs get remapped twice. ❓
- **Decal atlas pitfalls:** assign triangles to islands by stored triangle centroids, not by "centroid inside the island box" (padded boxes of neighbours overlap). Treat only zero-area UV triangles as degenerate – single-colour stripe decals use real triangles of ~2 px². If a decal material also uses its own normal map on UV0 (e.g. chrome lettering), build a parallel normal atlas with the same layout and do not rotate those islands (stored tangents would be wrong). A decal material that reads a vmask on UV0 (no vmaskUV2) changes its dirt pattern when remapped. Check whether the decal has a second UV set matching the body UV underneath (common on FS22 decals); then keep the body vmask and set `customShaderVariation="vmaskUV2"` so the dirt follows the surface (default_vmask would remove dirt entirely). Large decal quads (gauges, logos) limit how far a sheet can shrink. ❓ When composing the atlas, never alpha-composite islands onto a transparent canvas: colour under alpha 0 becomes black, block compression (BC7/DXT) then speckles edges (seen in game as black dots in chrome lettering ✅) and mips darken borders. Paste the islands and bleed colour into all alpha-0 pixels from the nearest visible pixel.
- **Logos as 3D relief instead of decals:** a chrome decal with a raised normal map only looks right from the front; from below or the side it is flat. Good truck mods model badge lettering as geometry. Technique: extract the outline from the decal texture (alpha or brightness, upscaled, `cv2.findContours` with RETR_CCOMP + `approxPolyDP`), place the points on the real decal surface via barycentric lookup over the decal triangles (follows bends), extrude walls plus a small chamfer (inner ring offset by mitre), triangulate the top with holes (`mapbox_earcut`), copy the winding from the decal, use the same chrome material as nearby trim, and collapse the decal triangles. Check emblems for mixed materials first (the FS22 TGS lion was split across two decal materials). ❓ Note: FS25_manTGX18500 models lettering as geometry; other packs keep a chrome decal.
- **Colourable truck chassis:** split the black slot of the chassis mesh into connected parts and classify by shape and position (horizontal cylinders of equal cross-section = air tanks, upright cylinders at the axles = air bellows, thin tall parts at the axles = dampers, long low parts at the rear axle = trailing arms, centre under the cab = engine/gearbox, far outboard = tanks/boxes/steps). Render a preview per group, let the player choose what stays black, and apply the rule before chassis variants are copied so all of them inherit it. ❓
- **Slimming `.shapes`: weld duplicate vertices.** Parts built or appended with three own vertices per triangle bloat the file (about 60 bytes per vertex). Merge only bit-identical vertices (every attribute including skinning) within one subset, reset the subset vertex ranges, then compare all triangle corners before and after. For size reference: the base-game Rudolph family (3 trailers) is about 63 MB, about 4 MB of shapes each, 2048² normal/vmask maps as BC7 (5.6 MB) or 2.8 MB. ✅
- **Performance against base-game trailers:** Rudolph DK 280/TDK 301 and PWO 24 have about 45–78 visible draw calls, 40,000–60,000 triangles and **no light with `castShadowMap`**. Turn shadows off on converted FS19 lights (a point light with shadows renders six shadow views; FS19 plate lights did this with 0.4 m range). Base-game clipDistance: body, hoses, bolts 300 m, decals 30–50 m, grain/smoke effects 100 m. To cut draw calls, merge static shapes with the same parent and the same render settings into one shape (one subset per material), bake node scale (normals with the inverse transpose), then **recompute index paths like `0>3|12` in the vehicle XML** – they also appear outside `i3dMappings`. ✅

## Duplicating an assembly (e.g. three grain doors instead of one) ❓
- Read the parts from the skinned merged mesh (triangles per bone) or from separate shapes. Transform them into the **local frame of the target node** (inverse world matrix; rotate normals and tangents too). Store them as unskinned shapes under copies of the nodes (same rotation, translation plus offset).
- Duplicate in the XML for every copy: the animation parts, the `movingTool`/`movingParts`, the effect subtree, and a discharge node listing all effect groups. Copy effect subtrees as XML: shapes can share a `shapeId`, and `skinBindNodeIds` must point at the copied joints.
- Wall faces whose visibility changes per option: move them out of the original mesh into their own shapes, grouped by the bone/node that switched them before. Cut extra openings by clipping against rectangles and interpolating every vertex attribute.
- Append new nodes at the end of their parent, so existing `i3dMapping` index paths stay valid.

- **Ribbed wall, strip copies (no new wall geometry):** below a line inside a flat panel, clip the wall into vertical strips (attributes interpolated): centre (hole, guides), two side strips of equal width, rest. Horizontal ribs run straight through, so copies fit at the cut edges: "none" = side strip copied to the centre, "three" = centre (hole, guides, screws) copied to the sides. Keep strip edges clear of lugs/brackets; assign decals by centroid instead of clipping. A long hand lever of the centre door may cross a side door – drop the levers in the three-door variant. ❓
- **Merged mesh with blend indices but no weights:** vertices and normals are in bone space, so a detached part can be attached unchanged as a shape under its bone node; an LOD1 bone that is only offset becomes a child group with that offset inside the LOD group. ❓
- **objectChanges in trailerConfigurations:** use only `visibilityActive` and list every switched node in every entry (also in an otherwise empty entry), otherwise the inactive values of the other entries decide. If `trailer` is bound by `configurationSets`, add one set per option and base set. ❓

- **Baked AO next to removed parts:** the vmask green channel holds baked ambient occlusion, so removing a part (e.g. door guides) leaves dark bands on the neighbouring wall. Sample the vmask along a line via barycentric UVs before closing an opening, and replace the shaded neighbour areas with copies from an unshaded spot. ❓
- **Re-bending a mitred lever:** keep the shaft, rotate the miter ring about the corner point (intersection of the centre lines) by half the angle and everything beyond by the full angle; rotate normals/tangents too, working in world space (bone space → world → rotate → back). ❓

- **Option that moves the discharge point (tipping chute):** move every stream it affects, not only the rear one: grain-door stream, particles, discharge nodes and their copies (e.g. three grain doors), each by the same offset from its own position. ❓ A grain-door stream without chute belongs at the lower edge of the door opening, in the plane of the door plate (as in the base-game Z 18051), not at the rear stream offset.

## Turning a drawbar trailer into a semitrailer ✅
- Delete the front-axle and drawbar components, drop their bone triangles from the merged mesh and point skin references to deleted nodes at a node of the main component with the same pose; remove their mappings, the first two `<wheel>` entries per configuration, hubs, joints, collision pairs and drawbar-only animations (e.g. one driven by `componentJointIndex`).
- Take the kingpin height above ground from a base-game semitrailer: ground = wheel node y − tyre radius (compare the actual tyres). Balance the remaining axles like the reference (restLoad, initialCompression).
- Put the landing gear 2.3–2.5 m behind the kingpin, otherwise it hits the tractor unit. Separate nodes for legs and crank plus a `moveSupport` animation and `<support animationName>`; lengthen the travel by the frame height difference.
- When copying collision shapes, copy the attachment block too (cooked CPU collision). Geometry only gives "Non-cpu collision mesh … cooked at runtime" and the collision did not hold the trailer.
- Hoses on a semitrailer: socket nodes on the frame front with `isTwoPointHose="true" outgoingAdapter="DEFAULT" socket="…"`, no parked hoses. ❓ Do not put them on a tipping body (they lift with it); use a chassis bracket just behind the body front and below its lower edge.

## Transferring edits to a sister model ✅
- Textures can be transferred too. When a model shares parts with a finished one, find identical triangles (position clusters after a KD-tree offset) and copy **UV1/UV2, normal and tangent**. The finished normal map and vmask, including all touch-ups, then apply to the new model. Project nearly identical triangles onto the closest source triangle with the same orientation, comparing face normals rather than vertex normals. Decide **per part, not per triangle**, otherwise one part ends up as a patchwork of two textures. Parts without a counterpart keep their own textures through extra material slots, which are also listed in the colour configurations.
- First check whether a "new" model contains parts of a finished one. Measure vertex distances with a KD-tree per bone, take the median offset and measure again. One base-game trailer contained the whole body of its sibling, shifted by about 2 mm, with 82–90 % of vertices within 0.3 mm. An exact comparison using rounded coordinates finds nothing at such offsets, so always search with a tolerance or an offset.
- A similar UV layout does not mean identical textures. Compare 16-px blocks of the old normal and specular maps before reusing masks.
- Do not invent new selection rules. Instead, find the triangles of the finished model whose material changed: compare against an older state, keyed by rounded corner positions. Group them into parts, then search the sister model for **identical parts** (same triangle count, size ±2 mm, world x/y ±5 mm, any z). Copy the material per triangle from the nearest source triangle, measured relative to the part's corner. Check first that no identical part in the source exists both with and without the edit.
- Compute world coordinates of each shape from the i3d hierarchy (translation and rotation).
- For added geometry such as bolts, do not use "nearest part", because small neighbouring parts win. Use the build layout instead: if the sister model is longer by an extra panel, keep the parts at the same place and repeat the affected section shifted. Afterwards, verify that every bolt base sits on a surface.
- When the sister model shares the UV1 layout, reuse the finished vmask through `vmaskUV2` and build UV2 with the same rule. If there are more wall panels than free areas in the mask, map the extra panel onto the area of a panel on the **opposite side**, mirrored horizontally (u → U0+U1−u). The two are never visible at the same time. When checking, sample only outer faces: inner faces share UVs and look like repeats.

## Removing leftovers of a former variant (e.g. tractor-unit hydraulics) ✅
- Such parts often sit in a shared "additional parts" shape, not in the chassis mesh. List the connected components (triangle islands) of **all** shapes in the region, with bounding box and node name, before you decide where to cut.
- Render the candidate group in a highlight color from the side, top and rear. Hide occluders such as the wheel, fender and frame rails. Hoses can run far away (e.g. across to the frame centre) and only show up in a view without occluders.
- Run a proximity check: list the components within about 3 cm of the group. Small caps or plugs right next to the box usually belong to the group. Spring hangers and frame parts do not.
- Remove whole components that lie fully inside one of a few boxes, so the step is idempotent. Then rebuild the bounding volume.
- Afterwards check the **baked AO** (vmask G) of the surfaces behind the removed part: they now show its baked shadow as dark spots. Render a side view with a z-buffer that samples vmask G per pixel, before and after, and list the newly visible pixels per component. Fix without re-baking: on that surface's texels, raise only the coarse part of G (Gaussian σ ≈ 2–3 texels; σ 10 leaves dark rims) to the clean height profile (e.g. 85th percentile per height band). Only brighten, keep uniform shadow bands, re-encode only the changed DXT1 blocks and their mip blocks. With stretched, multiply-used UVs (frame rails) treat the whole face, not a z range. This is not idempotent, so apply it once.

## Detaching parts from merged meshes ✅
- In a merged mesh (`skinBindNodeIds` plus `blend_indices`, no weights), vertex positions are stored in the shape space of the merged node, not in bone space.
- If you put an extracted part as a new shape under its bone, convert the positions with inv(W(bone)) · W(merged node), and rotate normals and tangents with the rotation part. Otherwise the part is offset twice and floats away from the vehicle.
- Store images from the Icon Generator show such floating parts clearly, so check them for stray geometry.
- To make a part of a merged mesh switchable: cut its triangles (e.g. one subset) into a new shape under the bone. Take the positions from the world positions times inv(W(bone)). Rotate normals and tangents with the rotation that maps shape space to world space (Kabsch fit over the vertices; check that the residual is near zero, i.e. the part is rigid). Clear the skinning flags. Remove the subset and its material id from the merged mesh. Put LOD0 and LOD1 into their own LOD group with the original `lodDistance`. Verify by comparing triangle centres before and after (KD-tree). ❓

### Dashed bevel lines on wider faces
- Old FS19 normal maps often have dashed bevel lines on long faces that are wider than thin strips (20–60 px), plus stray dots 1–2 px outside the UV island. In game this shows as regular notches along beam edges. A median along thin strips alone does not catch them.
- Fix that worked: for each long, axis-aligned face take the per-row median along the face (include 2 margin rows where no other island lies); replace deviations that are less than ~4 px tall across the face (dashes), keep taller ones (brackets, bolts). Renormalize. ✅ visually in the texture, in-game check pending ❓
- The `Texture was flipped with quality loss` warning can also hit a BC7 normal map, with a header identical to unaffected files. Base-game normal maps (e.g. Rudolph, Kröger) are DXT1, so saving the affected file as BC1 is consistent with GIANTS assets. Use a high-quality BC1 encoder (e.g. quicktex level 18: mean error ~2 vs ~7 with etcpak's fast BC1).
- Same warning after re-encoding an edited vmask that originally shipped as DXT1 as BC7 (other BC7 vmasks of the same mod stayed silent): write an edited texture back in its original compression – here BC1 – and the warning is gone. ❓ (fix pending in-game confirmation)
- **Measuring a profile (e.g. a board's top edge):** cut the triangles with a plane (e.g. z = const in the middle) and read the section. Filtering *vertices* by position fails: long faces only have vertices at their ends, so a vertex filter on the middle section misses whole profiles (here a hollow top profile 10 cm higher than the outer bead, which led to a wrong correction). Measure end posts separately. ✅
- **Notching a new body around existing posts:** when the new body's end frames must clear the original board's end posts but its side wall must not, build the end wall/frame/fields with a separate inner-edge rule ("end mode": narrower below the post height, normal above) instead of changing the shared inner-edge function – otherwise the side wall gets pulled in as well. ✅
- **Open low-poly parts and `recalc_face_normals`:** after removing hidden caps from screw heads (open cone, open washer ring) to save polygons, Blender's `bmesh.ops.recalc_face_normals` over the whole object flipped many of these open parts inwards – in game the heads looked transparent/dark with only edges visible. Tag the faces you create with a known orientation (e.g. `create_cone` gives outward normals) in an int face layer and run `recalc` only on the other faces; create the layer *before* creating the faces, adding a layer invalidates existing face references. Check by connected components: winding normal vs. vector from the component centre. ✅ (tested on the build output)
- **Clean corner joints for tube/square-tube braces:** corner cubes read as very crude in game. Better at the same polygon count: build square tubes as prisms with **mitred ends** (cut each end by a line given as point + normal, intersect the two side edges with it): a diagonal cut vertically against the post, and horizontally at the centre of the cross tube so the cut disappears inside the tube; let the post end at the height of the joint and run the round tube over it (T-joint, tube end flush with the post). ✅ (cubes rejected in game test)
- **Rebuilding a reference layout from another model without copying it:** split the reference mesh by bone and by connected component, print each component's bounding box (and for flat plates/bars the outline corners), and map the positions into your own model through shared landmarks (e.g. bottom edge of the side board and the hinge height give a linear height map; x stays 1:1 when the hinge lines match). Rebuild each part as your own primitives (prisms from the mapped outlines, cylinders). Check moving parts with your own kinematics: a reference model may fake a motion (static cable), so anchor points may need to move to give a real solution. ✅

### AO blotches on beams, alpha-tested gratings
- Old AO (vmask G) on straight frame beams often has blotches and steps along the beam. Replacing each row by its median along the long face keeps the cross profile and removes them. Process both triangles of a quad together (same UV box), otherwise each half gets its own median and a diagonal seam appears.
- Alpha-tested gratings seen at a grazing angle show regular teeth/moiré. Mitigation: close the holes in mip levels where holes are below ~1.5 texels (colour = bar colour mixed with a dark see-through tone by coverage). Base-game alpha parts (e.g. Rudolph DK 280) use alpha test without `alphaBlending`; trying `alphaBlending="true"` on the grating material is untested ❓.

- When cleaning a vmask (median, bilateral, deblocking), leave the R channel (scratches/wear) alone unless it is the problem. Wear consists of thin lines along edges and bevels, and a smoothing pass over all channels erases it: paint wear is then gone in game. Compare mean, p99 and the share of R > 20 before and after. ✅

### Sharp-edged light/dark rectangles on glossy paint: normal-map mips
- Symptom: slightly lighter or darker rectangles that follow face boundaries on clear-coated frame parts, mostly at mid distance. Diagnose by elimination: point the material's normal map to `$data/shared/default_normal.png` (or the vmask to `$data/shared/default_vmask.png`) on a test build and see which removes them. ✅ (normal map was the cause)
- Cause: mip 0 was flat on the faces, but standard mip generation blends bevel lines and neighbouring UV islands into thin faces (a 17 px beam face was tilted ~5° at mip 3). Clear coat makes every tilt visible.
- Fix: generate normal-map mips per UV face (each texel averages only texels of the face under its centre, empty texels assigned to the nearest face) and ease the lower mips toward flat. In-game result pending ❓
- Using `$data/shared/default_normal.png` on large painted parts removes such artefacts but makes the parts look flat and plain; good as a diagnosis, usually not as the fix.
- Grating with a toothed side edge: the hole rows of the alpha texture run right up to the UV border, so the mesh edge cuts through holes. Make the border columns/rows of the texture opaque (a frame).
- Notches along panel edges also appear on compact faces (aspect ratio below 4): a row of small spots (±4 in R/G) right next to a bevel line already shows as teeth in game. Process every face in both directions and, inside a band along each edge, set whole rows to their median along the face, keeping only details that are at least ~4 px tall across.
- To find which channel causes a spot on one face, profile the face along its length (e.g. tenths): normal R/G, AO, dirt, scratches, for mip 0 and lower mips. The channel that changes where the spots are is the culprit. A blocky dirt mask (vmask B) gives sharp-edged dust patches on beams; blur B only along the face (normalized over the face's texels).
- A light rectangle at a beam edge can also be a short break in the baked bevel line (in the old high-poly an attachment sat there). It spans the full bevel height, so a rule like "taller than 4 px across = detail" keeps it. On long rectangular faces, treat edge-band components shorter than ~25 % of the face length as notches. Never apply row-based rules to slanted or overlapping islands; restrict the result with a mask of long, non-overlapping rectangular faces.

### Chassis hoses on turntable (dolly) trailers
- The dolly is its own component, joined to the main frame by a joint rotating about y. Put dolly hoses under the dolly component (coordinates minus the component's translation) and main-frame hoses under the main mesh; join them at the turntable axis (a rotary-joint block), so steering keeps everything consistent. Base-game reference: Rudolph DK 280 RP. ❓ (in-game test pending)
- Main-frame hoses inside the dolly's swing radius must stay above the dolly's top edge.
- Several tubes changing sides together on a diagonal: same lateral offset for all, staggered start (outer lane first). Otherwise their normal distance shrinks to Δx·sin(angle).
- Rasterise free space first (occupied z ranges per line, y-z maps per x). Bottlenecks (e.g. a 14 cm gap in a cross brace) decide how many lines can pass; branch light cables at the rear from the electric socket instead of running them from the front.
- Mounting a transplanted air tank: hanging it freely between the frame rails looks wrong even with spacer blocks to a cross member. Mount it lengthwise under a main rail with its straps reaching the rail's bottom flange (bolted strap plates). When rotating a transplanted part, rotate normals and tangents too. ❓ (in-game check pending)
- Sister models with the same front and rear modules (e.g. a longer turntable trailer): measure the offset of the shared modules (dolly, gooseneck, rear end) and reuse the finished hose routes with a split shift (front part moved by the offset, rear unchanged, the straight channel in between simply gets longer). Only local differences (here: lower brackets at the rear) need overrides. ✅ (built and collision-checked; in-game check pending)
- Hoses that must follow the turntable at the rotary joint: skin the main-frame hose shape to two bones (`skinBindNodeIds="<main node> <dolly component>"`). In the .shapes file set HAS_SKINNING_INFO without SINGLE_BLEND_WEIGHTS, with 4 float weights and 4 index bytes per vertex. Near the axis, blend the dolly weight with a smoothstep from 1 at the joint block to 0 a few cm higher, and place extra tube rings in that zone (~6 mm). The engine then twists the bundle while steering, with no script. Linear blend skinning narrows the cross-section at large angles (w=0.5, 90° → ~71 %), so keep the blend zone close to the axis. ❓ (in-game check pending)
- Adding a small part as a yes/no configuration (e.g. a drawbar step) without Blender: build boxes in a part frame (u along the beam, v outward from the beam's outer face, y world height), map them with the rotation [n, up, d] (determinant +1, otherwise triangle winding flips) into the parent's coordinates, and put the group under the carrying component. Measure the beam from z-slices of the model. For tread plate, copy the paint material and only swap `detailNormal` to `$data/shared/detailLibrary/metallic/steelTreadPlate_normal.png` (detail maps are world-space, so no UV work is needed). In the colour configuration, list that slot with `materialTemplateUseColorOnly="true"` so the paint template keeps the tread detail. ❓ (in-game check pending)
- Frame-mounted parts on turntable trailers (e.g. side underrun protection): the front wheels come from external wheel files, so they are not in the i3d geometry. Compute their swing radius around the turntable axis from the tyre size (radius = rim/2 + width·aspect ratio, outer corner = hypot(track/2 + width/2, radius)), add the dolly geometry per height band, and keep everything on the frame outside that radius plus ~8 cm. Give the part its own colour with its own material slot and a `designColor5Configurations` block that lists the slot. Light grey like the real galvanised guard: `SHARED_GREY3` (colorScale 0.44); `SHARED_GREY` is dark (0.13). ❓ (in-game check pending)
- **FS22 base vehicle as a base (colorMask rule):** FS22 vehicleShader `colorMask`: `uv.y < 0` → `colorMat[floor(uv.x)]` (rgb + **w = layer in the detail array**), otherwise detail layer `floor(u)+floor(v)*8`. `staticLight` materials use colorMat too. The FS22 detail array (`data/shared/detailArray_*.dds`) is a DX10 texture array with 50 BC1 layers (specular R = smoothness, B = metallic); view the layers as a contact sheet and map them to FS25 material templates. FS22 `.shapes` are v7 and convert to v10 with the same reader/writer (add slot names). Raw FS19 v5 shapes (not re-saved in the editor) come out of the reader with **u and v swapped**. ❓
- FS22 vehicle XML is mostly accepted by FS25; remove shader lights (`defaultLights`, `brakeLights`, `reverseLights`, `turnLights`). FS25 puts the engine sound into the `motorConfiguration` (`<sounds><motor template="engineMedium" file="….gls"/></sounds>`), and sound templates were renamed (`switch01`, `attach01`, `waterSplash01`, …). A tipper truck type: `parent="tractor"` plus `fillVolume`, `dischargeable`, `trailer`, `cover`. ❓
- **Collision shapes need their convex-hull block in the shape attachment.** Without it the log shows `Non-cpu collision mesh … is being cooked at runtime`, and a vehicle's wheel shapes fail (`Wheel shape not found`, vehicle floats). Editor-saved v10 and FS22 v7 shapes carry it: `uint32 1, uint32 2, uint32 length, 'cm' 04 00, uint32 n, float margin (= min(0.04, 0.1 × smallest extent)), float volume, float[3] centre of mass, float[9] inertia per kg about the shape origin, n × float[3] hull points (planes moved inward by the margin)`. Keep it when rewriting shapes; raw FS19 v5 files lack it, so compute it (scipy ConvexHull). ❓
- **FS22 fixed detail layers carry their own colour.** Each layer of the FS22 detail array has a base colour (layer 1 "painted" is dark, about sRGB 45; layer 0 about 145; fabric layer 10 about 124). FS25 templates such as `metalPainted`, `calibratedPaint`, `fabric1` and `plasticPainted` have no `colorScale`, so they render white. Set `colorScale` to the layer's mean colour (linearised). ✅ (cause clear)
- **An FS25 `vehicleShader` material without detail maps shows a "256" placeholder pattern.** FS22 textured parts often had no `detailDiffuse`; in FS25 always assign a template (e.g. `plasticPainted`). ✅
- **Winding order = stored normal = outward.** In base-game shapes `cross(p1−p0, p2−p0)` points along the stored normal, which points outward. Generated geometry with the opposite winding shows only its inner faces in game. ✅
- **Tarps from FS19 bakes:** the old normal map often carries baked folds, bows and blocks on the tarp. Under FS25 lighting these show as dark lines and light/dark rectangles. The low-poly tarp already has its shape, so set the normal map flat inside the tarp's UV area (mask from the tarp triangles), keep the weave as a detail normal, and recompute the mips per UV island. Check first whether other parts share that UV area. ❓
- **Borrowing a missing UV2 from a sister model with the same texture:** the UV0 layout is the same. For each triangle, look up its UV0 centroid in the donor and apply the donor triangle's affine UV0→UV2 map, duplicating vertices where needed. Do the lookup **per material slot**, because parts often share UV0 areas with different UV2. The model can then use the same `vmaskUV2` materials. ❓ Caveat: this only works when the geometry matches. On larger faces (a truck body vs. the trailer) it produces blotches; there, fall back to UV2 = UV1 and point problem parts (e.g. the tarp) at a clean spot in the vmask.
- **Check in a game-like view, not in flat elevations.** A perspective z-buffer render with back-face culling (camera placed like the player's screenshot, plus a pixel pick that reports shape and material) finds "something pokes through" problems quickly. Always include skinned merged meshes: parts such as a fifth-wheel plate can sit on their own bone there.
- Shade such check renders with the stored vertex normals, not flat face normals: stretched faces look like wedges with flat shading but are smooth in game, and "fixing" them can create real holes. Sampling the vmask through UV1/UV2 in the same render lets you compare AO and dirt per wall field against a finished sister model. ❓
- **UV2 for a model with the same UV1 layout but different dimensions:** apply the sister model's UV2 rule (instance areas per outer wall). If the posts sit elsewhere, split the wall face at a post and map each part to the matching field of the template (piecewise linear in u, jump hidden under the post), so baked post shadows land on real posts. ❓
- **FS22 vmasks have no paint wear (R ≈ 0)** and AO/dirt in DXT1 blocks. Upgrade like an FS19 conversion: R from tilted normals (bevels) and island borders of the paint slots, broken up by noise, scaled to p99 ≈ 22–24; smooth G/B only over used texels. FS22 normal maps are already clean; the gain is per-island mips and BC7. ❓
- When refilling vmask island borders, never take the value from the "nearest trusted texel" inside the island. For narrow islands that texel often lies in the neighbouring island and leaves blotches. Keep used texels and fill only outside the islands; smooth per UV island (label image, weight 0 across labels). FS22 dirt (B) is fine-grained and shows up as speckled dust at low dirt levels in FS25, so smooth it per island (σ ≈ 3 px at ~250 px/m). ❓
- FS22 `Decal` materials map to the non-metallic FS25 `decal` template; chrome lettering (e.g. a grille logo) needs its own material with the `chrome` template's detail maps. ❓ On a flat, upright emblem the `chrome` template mirrors sharply (the horizon line cuts through the letters), unlike curved chrome trims; `silverScratchedShiny` gives an even, slightly satin shine. (Correction: a logo that looked half bright/half dark turned out to be one triangle of the decal quad left in the old material – when selecting faces by position, list every triangle of the area before blaming reflections.)
- **Stretching a cab at a cut plane:** put the plane in a gap of the vertex z values (histogram). If it sits right behind profiles (louvres, ribs), the transition faces turn into long wedges; flatten the profile ends in front of the cut onto the plain surface, so that the added length is a plain surface. Drop parts that no longer fit (e.g. an air intake between cab and body) instead of bending them. ❓
- When stretching a cab, move multi-part pipes (exhaust, air intake) with a shear that ramps from 0 at the lower connection to the full offset at the top; moving only the tall part leaves the lower bend behind. When you copy a subtree into another i3d, rewrite `skinBindNodeIds` to the new node IDs (`Failed to find skin bind node id` otherwise). FS22 colour names such as `color="MAN_BEIGECLASSIC"` do not exist in FS25; use `materialTemplateName`. The `motorConfiguration` name appears in the vehicle name in the HUD. ❓
- When cloning a skinned shape, remap `skinBindNodeIds` that point at the shape itself (bone 0) to the clone, or the clone stays invisible while the original is hidden. ❓

- **Duplicated decals in FS19 models** ✅: a decal shape can carry a same-named, slightly offset child copy, which shows as a doubled, smeared logo. Check for child shapes with the same name as their parent shape.
- **Mirroring copied geometry** : z' = 2·plane − z, negate the normal and tangent z, reverse the triangle winding. When shortening a drive shaft, keep the joint ends and compress only the middle tube.
- **Decal UV2 after re-laying wall UV2** 🔎 (own tooling, in-game check pending): decals using the vmask read dirt/AO through UV2; when the walls get a new UV2 layout, old decal UV2 point at unrelated texels (post shadows show inside logos). Cast a ray from each decal piece to the wall and copy the wall's UV2 at the hit point to all its corners.
- **MAN grille lettering, lion and type badges** 🔎: well-made FS25 MAN conversions use chrome detail maps (metallic/clear_diffuse + clear_specular, no colorScale) **together with** the FS22 normal map `$data/vehicles/man/tgsDecals_normal` (raised lettering; the FS22 TGS itself only references default_normal there). In game, non-metallic + normal map looked white and flat, chrome without the normal map turned bright or dark depending on the view angle, and self-made domed normal maps looked bad. The FS22 atlas also holds „TGX 26.640“, useful for building other type numbers from original glyphs.
- **Rotating drive shafts** 📖✅: FS22 trucks skin the drive line to bones under `movingParts` that are `<speedRotatingPart node="…" radius="0.1"/>` (parent rotated 0 −90 0, so local X is the shaft axis). A copied shaft needs its own speedRotatingPart node; take the axis from the bone position, not from a vertex average.
- **Small chrome lettering** 🔎: do not crop and upscale a low-resolution decal normal map (FS22 tgsDecals_normal is 512 px) – the bevels turn into steps and chrome reflections break up. Compute the normal map at full resolution from the lettering alpha instead (supersampled distance-to-edge → smoothstep bevel, width and slope measured on the original).
- **Small type numbers** ✅: the plain FS22 decal (tgsDecals material with default normal map, no chrome) looks best in game; for other numbers only swap the texture (built from original glyphs) and keep material, size and texel density.
- **Small type numbers: no chrome** 🔎: chrome on the flat faces of small lettering reflects the ground from low viewpoints and looks like holes. FS25 TGX conversions put type numbers on the plain decal material with a normal map; chrome is used only for the large grille lettering.
- **Tandem fenders from a single-axle fender** 🔎: front fender = front half plus its mirror (clamp vertices behind the mirror plane onto it to avoid a gap; mirror: negate normal/tangent z and tangent w, reverse winding), rear fender = original moved by the axle spacing; compress the inner halves slightly so they meet, and keep both brackets at the joint (double bracket). Moving the rear end by exactly the axle spacing keeps lights, plate holder and mudflaps as on the 4x2/4x4.

- **FS22 static lamp meshes (defaultLights/turnLights/brakeLights/reverseLights):** keep these XML blocks; FS25 `StaticLight` still reads `#node` or `#shaderNode`. The material must expose `lightControl` or `lightIds0` (else the log warns "Static lights not using 'lightControl' or 'lightIds0'"), or the entry needs `toggleVisibility="true"`. For FS22 meshes that carry the light colour per vertex, use the FS25 vehicleShader variation **`staticLight_vertex`** (emissive = vertex colour rgb × `lightIds[0].x`, no UV1 needed; the shader comments it as meant for porting FS22 vehicles). Give each lamp mesh its own material copy if the material is shared with non-lamp shapes. Symptom when missing: light cones work, lamp glass stays dark. ✅ confirmed in game.
- **Porting a finished vehicle's details to a related model by component matching:** treat connected triangles as components; two components match when triangle count and bounding-box size agree (±2 mm) and the x/y centre agrees after an offset found by voting (z free). Copy the material per triangle from the nearest source triangle relative to the component corner; with several identical source components use the most common colour pattern. Parts added later (e.g. bolts) are found as vertices missing from the original model; attach each to its carrier component (smallest bounding box ±1.5 cm around the part centre — vertex distance fails on long beams that only have corner vertices) and replicate it on every matching carrier in the target. 🔎 (own tooling, visually checked, in-game test pending ❓)
- **Copying whole sub-trees between models with the same node structure:** if the target parent is only translated (no rotation), child nodes can keep their local transforms; copy shapes byte-identical with new shapeId/nodeId, copy materials by name, and remap `skinBindNodeIds` per copy (otherwise a second copy binds to the first copy's joints). Parts that live inside a skinned merged mesh can be rebuilt as a standalone shape from the triangles of their bone, in bone space. 🔎
- When rewriting the same shape several times with a shapes writer, keep the original attachment tail; after the first rewrite the serialized prefix no longer matches. 🔎
- **FS22 MAN TGS 18.500 details:** the headlight guards are not a separate node; they are an alpha decal inside `decalsExterior2` plus a frame inside `additionalParts`. To make them optional, split those components into their own shapes and toggle them with a yes/no `designNConfigurations`. The chassis frame shares the generic `black_mat` slot; for a colour option, move the rail and crossmember components into their own material slot and use `designColorNConfigurations` with `<material materialSlotName="…"/>`. Do this before cloning variants so the clones inherit the slot. 📖 (in-game test pending ❓)
- **Centering a wheel under a fender:** measure the opening of the fender's outer lip at several heights (vertices near the outermost x, largest z gap per height) instead of the bounding box, which thick rear lips and brackets skew. An offset of ~1.5 cm is already visible in game. For tandem axles, use two unmodified copies of the single-axle fender and set the axle spacing to fender length + a small gap; mirrored or compressed halves give openings of different sizes. ✅ (seen in game)
- When you move mesh parts (fenders, axles), also move the link nodes that sit on them: shared-library reflectors and lights (`<sharedLight linkNode="…" filename="$data/shared/assets/reflectors/…"/>`) are separate TransformGroups and stay behind otherwise. For optional add-ons (yes/no configuration), split their mounting clips out of the base mesh too, or they remain visible when the add-on is switched off. ✅ (seen in game)
- **Adding simple parts by script (grilles, lamp guards):** build them from boxes in a new shape entity; copy the vertex layout from an existing non-skinned shape without vertex colours and take the triangle winding from it. For single-colour painted parts, give every vertex one UV (centre of the largest triangle of that material) and let the colour configuration paint it. Attach new nodes as **children** of a leaf node (the wall, the light's link node): sibling indices of other nodes stay unchanged, so existing `i3dMapping` paths remain valid, and the part inherits visibility and position from its parent. Extra child shapes under a `<sharedLight linkNode>` node are fine. ❓ (in-game test pending)
- **Copying parts out of a skinned mesh into a new rigid shape** (e.g. mudguards onto a steering turntable component): transform the triangles to the target component's frame (rotate normals/tangents too), drop blend indices/weights **and** clear the HAS_SKINNING_INFO / SINGLE_BLEND_WEIGHTS bits in the shape options, otherwise skin data is still expected. Append the shape as the last child of the component so it moves with it and no existing index path shifts. ❓ (in-game test pending)
- **Moving an assembly (e.g. an axle) inside a merged mesh:** selecting parts that lie completely inside a z window leaves parts at the window edges behind (spring hangers, one spring leaf, a brake crank), which then looks stretched. Select the whole connected assembly, or compare with the previous state afterwards and check per part whether it moved; render before/after from the same side view. ✅ (seen in game)
- **Dark streaks or round marks on flat surfaces** after reusing another model's texture atlas usually come from the normal map or the vmask (dirt/wear), not from geometry. Overlay the triangles' UVs on those textures to find the cause, then move the affected triangles (with their own vertices) to a flat texture area, or compress their U range into a clean part of the tile. ✅ (seen in game) The vmask (dirt/wear/AO) is read with the **second UV set**, the normal map with the first – fix vmask streaks in UV1. When remapping, give the affected triangles their own vertices and assign planar UVs; changing only vertices whose fractional u lies in a range misses vertices at u = 1.0 and stretches the face. ❓ (in-game test pending)

- **When moving a body part, move number-plate nodes and decals with it.** A rear fender with mudflap was moved back 1.6 cm; the rear `licensePlate` node, the logo decal it hides and a logo decal inside a merged decal shape stayed behind and ended up 1.5 cm *inside* the mudflap: no plate, no logo, no log message. In the original the plate node sits about 0.5 mm and decals about 3 mm behind the visible surface. Check with a ray cast from behind at the plate position against every shape. The plate itself is created at runtime at that node, so offline renders never show it. ✅ (cause measured)
- **Taking an add-on part (bull bar etc.) from an FS19 mod on the same base vehicle:** positions match after adding the FS19 node offset. FS19 colorMask parts (material array zone, e.g. chrome) need no texture: copy positions and normals, derive tangents from the normal, set UV0 to one constant texel of an existing chrome material and UV1 to the body UV of the nearest body point for dirt, even when the part stands in front of the body. Attach it as the last child of a configuration node and switch it with a yes/no configuration; that configuration can also move the front plate node (`objectChange translationActive`). ❓ (in-game test pending)

- **Halving texture size like the base game:** base-game normal maps are DXT1/BC1 (4 bits per pixel); BC7 needs twice as much at the same resolution. To convert an already cleaned BC7 texture, decode every mip level and encode each one as BC1 (quicktex level 18) instead of rebuilding the mips: 4096×2048 went from 10.7 to 5.3 MB with a mean error of 1.3–1.9/255. To know where to look in game, map the BC7-vs-BC1 error image back onto the UV0 triangles of the shapes that use that normal map and report their world positions. ❓ (in-game test pending)

- **Slimming a .shapes file without visible change:** after many scripted edits a shapes file carries (a) shapes no node references, (b) unused vertices left behind when triangles were removed (one axle mesh had 16,370 vertices for 2,368 triangles) and degenerate triangles, (c) content-identical shapes (the same parts for two body variants, short/long LOD copies). Remove (a), rebuild each subset with only referenced vertices for (b), and point several `<Shape>` nodes at one `shapeId` for (c) – GIANTS exports do this too (e.g. the wipers in a FS25 MAN TGX mod). Leave physics/collision nodes alone. Run it as the last build step. Truck 27.2 → 24.0 MB; offline renders before/after were pixel-identical. ❓ (in-game test pending)
- **Before merging two similar textures**, rasterize each model's UV usage and count differing pixels that both models use. Two trailer normal maps were 96 % identical, but 150,000 used pixels differed (fixed separately per model), so they could not be merged. A 50 %-filled atlas does not necessarily fit into half the area: repack the island rectangles first (here only at 0.78 scale).

- **Dirt UVs for parts standing off the body** (bull bar 10–20 cm in front of the cab): copying the body UV of the nearest body point per vertex only works for parts lying on the body (badges, logos). With a gap, neighbouring vertices pick different UV islands and the vmask is smeared into streaks (check: UV1 pixels per metre of edge; ~400 is fine, here up to 600,000). Project such parts flat instead (x→u, y→v, ~70 px/m) onto a calm vmask patch with a typical body dirt value (dirt channel near the body median, lowest variance, inside used body UVs). A patch whose dirt channel is 0 never gets dirty. ✅ (cause seen in game)
- **No hoses on the front hitch:** `<connectionHoses><target attacherJointIndices="…">` decides at which attacher joints a target exists. Templates taken over from FS22 trucks may list the front hitch too (e.g. `"2 3"`), so hoses of a front-hitched trailer get pulled to the rear sockets. Remove the front joint index – with no target, the trailer's hoses stay parked. ❓ (in-game test pending)

- **Copying the dirt look of a part from a sister vehicle:** if both vehicles share a part (same triangle count, congruent after an offset), split it out of the merged mesh into its own shape (only if it is bound to a rigid bone), give it copies of the own materials but with the donor's normal map and vmask and the donor's UV channel (e.g. UV0 instead of `vmaskUV2`), take UV0 per vertex from the nearest donor vertex and recompute tangents from the new UVs. Add new paint materials to the colour configuration (`materialSlotName`). For parts without a counterpart, stretch them onto a similar donor part by their extents before taking the nearest point – plain nearest-point transfer over a large gap collapses all vertices onto one edge. **Mind UV seams:** at every seam two vertices with different UVs share one position, so "nearest donor vertex" mixes UV islands and stretches triangles across the texture (seen in game as a raster pattern ✅). Build islands from vertex indices (not positions), pick one island per triangle (nearest donor triangle with matching shading normal – mirrored sides have reversed winding, so face normals are unreliable) and project the corners onto that island only. Check: UV area / world area per triangle must not exceed the donor's maximum. ❓ (in-game test pending)

## FS22 base-game vehicles in an FS25 mod (map start vehicles)
Learned while porting nine FS22 start vehicles (trailers, implements, tractors, a combine) into a private map mod.
- ✅ **Paths inside a mod vehicle XML are relative to the mod root, not to the XML's folder.** `<filename>dk115.i3d</filename>` in `vehicles/welger/dk115/dk115.xml` was looked up in the mod root ("i3d … could not be found"). Write `vehicles/welger/dk115/dk115.i3d` (same for `<image>`, effect textures and sound files).
- ✅ A map's `defaultVehiclesXMLFilename` (savegame format) can load mod vehicles with `filename="$moddir$ModName/vehicles/…/x.xml"`. Give one `<component index="i" position rotation/>` per i3d root component: world position = vehicle position + yaw-rotated local root translation.
- 📖 FS22 colour system: `<baseMaterial>` (and the first option of `baseMaterialConfigurations` / `designMaterialConfigurations`) overwrite the i3d `colorMatN` values at runtime; the i3d values may be placeholders. When converting colour zones to separate FS25 materials, bake these colours into `colorScale`. FS22 `brandColors.xml` names mostly exist as FS25 `brandMaterialTemplates` with the same values. A `material="N"` on a shaderParameter changes the detail layer (template).
- 📖 FS22 sound templates are FS25 templates in camelCase without underscores (`SWITCH_01` → `switch01`, `HONK_VALTRA` → `honkValtra`, `ATTACH_01` → `attach01`). Not found: `hydraulicLayerTone*`, `defaultHydraulicSound` (use `hydraulicClose01`/`hydraulicOpen03`), `grainTankFill` (`grainTankMediumFill`), `HONK_JD_HARVESTER` (`honkJohnDeereHarvester`). `.wav` paths resolve to the FS25 `.ogg`; `transmission/transmissionLoop.wav` is `transmissionLoop01`.
- 📖 FS22 tyre, hub, dual-rim, reflector, wheel-chock, beacon and number-plate-light paths still exist in FS25. FS22 upper links `upperLinks/walterscheid0X.i3d` do not; FS25 uses XML files (`walterscheidHO_90_600.xml`, `walterscheidSO_65_460.xml`, …) and `materialTemplateName` instead of `color`.
- 📖 `<rimColor>X</rimColor>` → `<rimMaterial materialTemplateName="X"/>`, hub `<color0>` → `<hubMaterial materialTemplateName="X"/>` (both inside `<wheels>`). Drop `color`/`material` on `wheelChock`.
- 📖 Collision masks: `2109442` → group `0x10004` mask `0xfe3ffb83`; `1073741824` (exactFillRootNode) → `0x40000000`/`0x20000000`; `1048576` (tension-belt trigger) → `0x20000000`/`0x100000`; `18874368` (dynamicMountTrigger of a header trailer) → `0x20000000`/`0x10000`.
- 📖 FS22 vehicleShader `Decal_normalThirdUV` (decal, vmask via UV2, normal map via UV3) → FS25 variation `vmaskUV2_normalUV3` with the `decal` template and `alphaBlending`. `Decal_colorMask` materials need `alphaBlending="true"`.
- ✅ Remove `referenceId` attributes from converted i3d files: they point at the old `<File>` ids (editor references such as reflectors or wheel chocks, which the XML loads anyway); after renumbering the files they point at textures.
- FS22 shapes (v7) keep their collision hull attachment; re-serialise the v7 prefix and append the original tail when writing v10.
- Textures from **other FS22 vehicle folders** (e.g. canola modules, front-weight frames) must be copied as well, or the log shows "Missing png file".
- 📖 FS22 `uvScroll_colorMask` → FS25 `uvTransform` (parameter `offsetUV`); FS22 `meshScroll_colorMask` → FS25 `meshScroll` (the parameter is `scrollPos`, not `scrollPosition`; keep `lengthAndRadius`).
- ❓ A combine pipe unload trigger (`trailerTrigger`) needs FILLABLE (bit 30) in its mask: `collisionFilterGroup="0x20000000" collisionFilterMask="0x40000000"`.
- FS22 accepted `-` placeholders in vectors (`rotDriveRotation="- - 0"`); FS25 fails to parse them, use `0`.
- Missing sounds: `vehHydrostaticTransmission_BgMN01` → `vehHydrostaticTransmission_01`, `cabin/indoorCabinRumbleLoop` → `cabin/vehIndoorCabinRumble_01`. FS25 wants `categoryRange` or `widthRange` on `bottomArm`.
- ✅ Fixed FS22 detail layers carry their own colour (see the FS22 colorMask notes). If the per-layer colour table is missing, those parts (black paint, seat fabric, …) become white in FS25.
- 📖 FS22 `secondUV_*` variations read the vmask via UV2 → FS25 `vmaskUV2` (`uvTransform_vmaskUV2`/`meshScroll_vmaskUV2` with scrolling); `Decal_normalThirdUV_colorMask` → `vmaskUV2_normalUV3`. Otherwise dirt and AO appear as a foreign pattern on the part.
- FS22 tractors have no `exactFillRootNode` for the diesel unit ("Missing exactFillRootNode for fuel fill unit"). Add an invisible box `exactFillRootNodeFuel` (kinematic, compound, `0x40000000`/`0x20000000`, with collision hull attachment) as the last child of the main component and reference it in the diesel `fillUnit`. FS22 `fillTypes` may be lower case (`diesel`).
- 📖 FS25 sound template `transmissionHarvester` points to a missing file (`vehHydrostaticTransmission_BgMN01.wav`); give the `gearbox` an explicit `file` (e.g. `vehHydrostaticTransmission_01.wav`). A `fruitExtraObject` with `fruitType` must not also have `isDefault`.

## ModHub TestRunner and GIANTS Icon Generator ✅
- TestRunner checks (seen failing/passing): current `descVersion` (116), version `a.b.c.d` with a ≥ 1, English title words capitalised, mod icon 512×512 as **DXT1** (DXT5 fails with "excessChannel"; store images may be DXT5), a changelog in the description once the version is not 1.0.0.0 (checked for en/de, e.g. "Changelog 1.0.0.1:"), `<size height>` on every vehicle, no zero-triangle shapes (turn them into empty TransformGroups so index paths stay). - "Mod Icon" mode composites the ModHub background itself. "Store Icon" mode writes `store_<name>.png` + `.gim` into the mod folder and does not touch existing DDS files: convert yourself (512, DXT5, no mips) and remove the PNG/.gim from the release (ObsoleteFiles).

### Cleaning up after a boolean union; wear only on convex edges (❓ technique, visual result confirmed in renders only)
- An EXACT union of touching parts (welds, rails, posts on sheets) leaves coplanar same-facing overlaps (z-fighting) and internal back-to-back contact faces. Embedding parts by 0.5 mm made it worse (twice the triangles, many more overlaps).
- Post-pass: group triangles by plane (normal rounded to 0.01, distance to 0.5 mm). Delete a triangle whose area (sampled at ~36 barycentric points) is fully covered by remaining same-facing triangles of that plane, smallest first so no holes appear. Also delete triangles fully covered by opposite-facing ones (internal contact faces) – only valid if there are no zero-thickness sheets. Example: 21.7k → 19.2k triangles, overlaps 425 → 58.
- Edge wear in the vmask: merge edges by their supporting line (T-junctions after the union otherwise look like open edges) and draw wear only on convex edges with > 30° dihedral; concave corners (rail on sheet) produced a bright wear line across panels.
- To keep ~90 % paint on thin struts, multiply the wear by a sparse spot mask (blurred noise, top ~10 %) after the offset subtraction.
- Height-based dirt for add-on parts: use absolute height in the vehicle frame, not the object's own min/max, or the top of a small extension gets as dirty as the bottom of the trailer.
- Height-based dirt from a UV raster: rasterize the height from **all** material groups that share the atlas. If only one group is rasterized, texels of the others (e.g. galvanized ladders) inherit the height of the nearest rasterized texel and get dirt in the wrong places. Also do not derive edge wear from UV island borders after a union: the union splits flat panels into many islands and every border becomes a wear line.
- Frame corners that look like two profiles pushed into each other: build the whole perimeter rail as one closed sweep with a bend radius per node (arc around axis d0×d1, centre on the bisector at R/cos(θ/2), rings shifted onto the bisector plane for a constant section). Square parts under the bend (corner angles) should end below the rail, otherwise their sharp corner sticks out of the bend. (❓ visual result checked in renders only)
- Flush parts still look separate when the coplanar pieces sit in differently rotated UV islands: the detail-map grain changes direction at every joint. Use a world-planar UV1 per plane for the detail maps (u = normalize(up × n), v = n × u; tangent = u axis) and move the baked atlas to UV2 with `customShaderVariation="vmaskUV2"`. (❓ untested in game)
